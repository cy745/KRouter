# ksp-collector

跨模块注解收集工具库，专为 KSP 处理器设计。

## 解决的问题

在 KMP 多模块项目中，KSP 处理器通常只能处理**当前模块**的注解。如果需要在**主模块**中聚合所有依赖模块的注解信息，需要一套跨模块的元数据共享机制。

`ksp-collector` 提供了标准化的两阶段流程：

```
依赖模块 A (collect)        依赖模块 B (collect)        主模块 (read)
     │                          │                          │
     ├─ 扫描 @YourAnn           ├─ 扫描 @YourAnn            │
     ├─ 生成 Metadata_A         ├─ 生成 Metadata_B          │
     │  (到共享包)               │  (到共享包)               │
     │                          │                          │
     │                          │                          ├─ getDeclarationsFromPackage()
     │                          │                          │  → Metadata_A 引用 A 的类
     │                          │                          │  → Metadata_B 引用 B 的类
     │                          │                          │  → 合并去重
     │                          │                          │
     │                          │                          ├─ 你自己的代码生成
```

## 接入步骤

### 1. 添加依赖

```kotlin
// build.gradle.kts — 你的 KSP 处理器模块

dependencies {
    // ksp-collector 包含 MetadataCollector + MetadataReader
    implementation("io.github.cy745.KRouter:ksp-collector:0.0.7")
}
```

只有最简依赖：`ksp-api` + `kotlinpoet` + `kotlinpoet-ksp`。不依赖 KRouter 或其他业务框架。

### 2. 在依赖模块配置收集（collect）

依赖模块通过配置 `kRouterType=collect` 来运行收集逻辑：

```kotlin
// 依赖模块的 build.gradle.kts
plugins {
    kotlin("multiplatform")  // 或 kotlin("jvm")
    id("com.google.devtools.ksp")
}

ksp {
    arg("kRouterType", "collect")  // 指定使用收集处理器
}

dependencies {
    add("kspJvm", project(":my-processor"))  // 你的 KSP 处理器
}
```

> 如果依赖模块不需要自定义注解收集，可以跳过这一步——主模块会在第二轮通过
> `getDeclarationsFromPackage()` 自动找到所有已编译的 metadata。

### 3. 在你的 KSP 处理器中使用

```kotlin
package com.example.processor

import com.google.devtools.ksp.processing.*
import com.google.devtools.ksp.symbol.*
import com.lalilu.kspcollector.CollectorConfig
import com.lalilu.kspcollector.MetadataCollector
import com.lalilu.kspcollector.MetadataReader

class MyProcessor(env: SymbolProcessorEnvironment) : SymbolProcessor {

    private val collector = MetadataCollector(
        CollectorConfig(
            annotations = listOf(
                "com.example.MyAnnotation",  // 你要扫描的注解
            ),
            sharedPackage = "com.example.generated",  // metadata 输出包
        ),
    )

    private val reader = MetadataReader("com.example.generated")

    private var readPhaseDone = false

    override fun process(resolver: Resolver): List<KSAnnotated> {
        if (readPhaseDone) return emptyList()

        // 第一轮：收集当前模块的注解，生成 metadata
        val metadataName = collector.collect(resolver, environment.codeGenerator)
        if (metadataName != null) {
            // 返回 metadata 类 → KSP 触发下一轮（metadata 被索引）
            return listOf(resolver.getClassDeclarationByName(metadataName)!!)
        }

        // 无注解 → 尝试读取跨模块 metadata（第二轮+）
        val allClasses = reader.readWithFallback(
            resolver = resolver,
            ownAnnotations = listOf("com.example.MyAnnotation"),
        )

        if (allClasses.isEmpty()) {
            // 真的没有任何注解
            return emptyList()
        }

        // ── 你的生成逻辑 ──
        allClasses.forEach { clazz ->
            // clazz 是 KSClassDeclaration，可能来自任何依赖模块
            val annotation = clazz.annotations
                .first { it.annotationType.resolve().declaration.qualifiedName?.asString() == "com.example.MyAnnotation" }
            // ... 生成代码
        }

        readPhaseDone = true
        return emptyList()
    }
}
```

### 4. 注册处理器

```kotlin
// src/main/resources/META-INF/services/com.google.devtools.ksp.processing.SymbolProcessorProvider
class MyProcessorProvider : SymbolProcessorProvider {
    override fun create(env: SymbolProcessorEnvironment): SymbolProcessor {
        return MyProcessor(env)
    }
}
```

## API 参考

### `CollectorConfig`

```kotlin
data class CollectorConfig(
    val annotations: List<String>,    // 要扫描的注解 FQN 列表
    val sharedPackage: String,         // metadata 输出包名
    val kdoc: String = "Generated by ksp-collector. DO NOT MODIFY.",
)
```

### `MetadataCollector`

```kotlin
class MetadataCollector(config: CollectorConfig) {

    /** 扫描注解并生成 metadata 类。返回 metadata 类名，无注解时返回 null。 */
    fun collect(resolver: Resolver, codeGenerator: CodeGenerator): String?
}
```

### `MetadataReader`

```kotlin
class MetadataReader(sharedPackage: String) {

    /** 读取共享包中所有 metadata 类引用的被收集类列表。 */
    @OptIn(KspExperimental::class)
    fun readCollectedClasses(resolver: Resolver): List<KSClassDeclaration>

    /** 读取跨模块 metadata + 当前模块注解，合并去重后返回。 */
    @OptIn(KspExperimental::class)
    fun readWithFallback(
        resolver: Resolver,
        ownAnnotations: List<String>,
    ): List<KSClassDeclaration>
}
```

## 两轮处理原理

| 轮次 | 状态 | 行为 |
|------|------|------|
| 第一轮 | `collect()` 有结果 | 生成 metadata → 返回 metadata 类 → KSP 调度下一轮 |
| 第一轮 | `collect()` 无结果 | 注解都来自依赖模块 → 进入第二轮检查 |
| 第二轮 | `readWithFallback()` 有结果 | 读取跨模块 metadata + 当前模块注解 → 执行生成 |
| 第二轮 | 仍为空 | 无任何注解，跳过 |

关键点：

- **metadata 跨轮次可见性**：KSP 的 `getDeclarationsFromPackage()` 在第一轮无法看到同一轮生成的文件，但在第二轮及以后可以读到所有已编译的 metadata（包括依赖模块的）。
- **当前模块自己的注解**：第二轮中当前模块自己的 metadata 由 `collect()` 刚刚生成、同轮不可见，因此 `readWithFallback()` 会额外调用 `getSymbolsWithAnnotation()` 直接补充。

## 与 kctfork 测试的兼容性

如果使用 kctfork 做单元测试，单轮编译环境下 `getDeclarationsFromPackage()` 可能返回空。
此时 `readWithFallback()` 的 `ownAnnotations` 参数会确保当前模块的注解仍然能被正确收集。
